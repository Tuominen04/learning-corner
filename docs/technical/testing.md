# Testing

> **Audience:** People building Personal Learning Corner
> **Status:** Planned
> **Last reviewed:** 2026-09-06

There is no server, no network, and one user. That removes whole categories of testing and
concentrates the risk in one place: **the library on disk.** Test accordingly.

## What the risk actually is

Ranked by how bad it is when it happens:

1. **User data is lost or corrupted** — a bad write, a wrong conflict resolution, a migration
   that eats a field. Unrecoverable, and it ends the user's trust permanently.
2. **A citation is silently wrong** — the product's whole claim is that it gets this right.
3. **A parallel text is silently misaligned** — the learner cannot detect it, which is what
   makes it serious.
4. **The application will not start.** Bad, but the library is still there and readable.
5. **The interface is wrong about pixels.** Annoying.

Testing effort follows that order, not the order things are easy to test.

## Layers

### Engine unit tests

The bulk of the suite, in the engine repository. Pure logic, no filesystem where avoidable:

- **Citation formatting** — table-driven fixtures from the APA manual's own examples, covering
  every rule in [Citation model](citation-model.md): author counts, group authors, missing
  dates, all three disambiguation cases, locator kinds, reference ordering.
- **Segmentation and alignment** — each unit, the `~` and `+ ` markers, misalignment
  detection and the line it reports, repeated segments.
- **Comparison logic** — every row of the [three-outcome table](backup-and-sync.md#the-three-outcomes)
  as its own case.

### Filesystem tests

Against a real temporary directory, because the filesystem is what we are actually testing:

- Round-tripping every entity: write, read, compare.
- Hand-edited files: valid changes are picked up; broken front matter produces a clear
  diagnostic and no data loss; duplicate identifiers are detected.
- Migration from every previous format version, using **real libraries kept as fixtures** —
  saved at each format version, never regenerated by current code. A migration test against a
  library the current code produced tests nothing.
- Unicode paths, long paths, read-only directories, a full disk, a removed drive mid-write.

### Two properties worth asserting directly

These encode the two architectural promises, and if either breaks, a principle has been
violated somewhere:

**Rebuild equivalence.** For a library fixture: record the result of every read operation,
delete `.plc/`, rebuild, and assert every result is identical. This is what keeps the index
derived ([Search index](search-index.md)).

**Backup round-trip.** For a library fixture: back up, restore into a fresh location, and
assert the two libraries are byte-identical outside `.plc/`. Then the harder variant —
modify both sides, run the comparison, resolve each conflict every possible way, and assert
that in every case nothing that existed on either side is unrecoverable
([Backup and synchronisation](backup-and-sync.md)).

### Contract tests

One suite asserting every operation in [Engine contract](backend-contract.md): its inputs, its
result shape, and the errors it produces for each failure. This suite is what makes the
contract normative rather than aspirational.

It lives in the engine repository and runs against no interface at all, which is the property
that keeps the boundary honest — logic that leaked into the interface cannot be tested here,
and its absence shows up as a gap.

### Interface tests

Component tests for the editor, the pane selector, and the map. End-to-end tests for the
journeys a break in which would be unmissable: create a library → write a document → save a
source → cite it → see the reference list; and create a work → add editions → toggle panes.

Kept deliberately few. End-to-end tests are slow and brittle, and the risks that matter are
one layer down.

### Manual verification

The release checklist in [Packaging for Fedora](packaging-fedora.md#verifying-a-build),
including the offline run and the uninstall check.

## Fixtures

A set of small libraries checked into the engine repository:

| Fixture | Exercises |
| ------- | --------- |
| `minimal` | An empty library |
| `citations` | Every source type, every disambiguation case |
| `parallel` | The Russian/Finnish work, including misalignment and a repeated chorus |
| `unicode` | Cyrillic and Finnish text, accented filenames, locale-sensitive sorting |
| `damaged` | Broken front matter, duplicate identifiers, an orphaned citation |
| `v1`, `v2`, … | One library per historical format version, frozen forever |

`damaged` is the one people skip. It is also the one that decides whether a user with a
half-broken library gets a diagnostic or gets nothing.

## In CI

On every pull request: engine unit tests, filesystem tests, contract tests, both property
tests, interface component tests, clippy and rustfmt, the interface's linter and type check,
and `bash docs/check-docs.sh`.

On a release tag: everything above, plus the RPM and Flatpak builds and the manual checklist.
