# Testing

> **Audience:** People building Learning Corner
> **Status:** In progress — M1 implemented
> **Last reviewed:** 2026-10-19

There is no server, no network, and one user. That removes whole categories of testing and
concentrates the risk in one place: **the library on disk.** Test accordingly.

## What the risk actually is

Ranked by how bad it is when it happens:

1. **User data is lost or corrupted** — a bad write, a wrong conflict resolution, a migration
   that eats a field. Unrecoverable, and it ends the user's trust permanently.
2. **A citation is silently wrong** — the product's whole claim is that it gets this right.
3. **A parallel text is silently misaligned** — the learner cannot detect it, which is what
   makes it serious.
4. **The application will not start.** Bad, but the library is still there and readable.
5. **The interface is wrong about pixels.** Annoying.

Testing effort follows that order, not the order things are easy to test.

## Layers

### Engine unit tests

The bulk of the suite, in the engine repository. Pure logic, no filesystem where avoidable:

- **Citation formatting** — table-driven fixtures from the APA manual's own examples, covering
  every rule in [Citation model](citation-model.md): author counts, group authors, missing
  dates, all three disambiguation cases, locator kinds, reference ordering.
- **Segmentation and alignment** — each unit, the `~` and `+ ` markers, misalignment
  detection and the line it reports, repeated segments.
- **Comparison logic** — every row of the [outcome table](backup-and-sync.md#the-outcomes)
  as its own case.

### Filesystem tests

Against a real temporary directory, because the filesystem is what we are actually testing:

- Round-tripping every entity: write, read, compare.
- Hand-edited files: valid changes are picked up; broken front matter produces a clear
  diagnostic and no data loss; duplicate identifiers are detected.
- Migration from every previous format version, using **real libraries kept as fixtures** —
  saved at each format version, never regenerated by current code. A migration test against a
  library the current code produced tests nothing.
- Unicode paths, long paths, read-only directories, a full disk, a removed drive mid-write.

### Two properties worth asserting directly

These encode the two architectural promises, and if either breaks, a principle has been
violated somewhere:

**Rebuild equivalence.** For a library fixture: record the result of every read operation,
delete `.plc/`, rebuild, and assert every result is identical. This is what keeps the index
derived ([Search index](search-index.md)). Two companions belong with it: that **incremental
writes agree with a full rebuild** — the incremental path is the one that runs constantly, so a
divergence there is the one that bites — and that a **corrupt index is discarded and rebuilt**
rather than surfaced as an error.

*Implemented in the engine repository as `tests/rebuild_equivalence.rs`.*

**Backup round-trip.** For a library fixture: back up, restore into a fresh location, and
assert the two libraries are byte-identical outside `.plc/`. Then the harder variant —
modify both sides, run the comparison, resolve each conflict every possible way, and assert
that in every case nothing that existed on either side is unrecoverable
([Backup and synchronisation](backup-and-sync.md)).

Around it, on real folders, the cases the specification turns on:

- every row of the [outcome table](backup-and-sync.md#the-outcomes) produced deliberately, and
  each question answered every way it can be, with the losing version found in `.conflicts/`;
- an apply that fails partway, then a fresh plan showing only what was left;
- a file changed between plan and apply, refused with `Conflict` before anything is touched;
- two copies of one library, each keeping its own last-agreed state;
- the frozen `v1` fixture restored and read exactly as it reads in place, and a newer format
  refused at plan time.

### Contract tests

One suite asserting every operation in [Engine contract](backend-contract.md): its inputs, its
result shape, and the errors it produces for each failure. This suite is what makes the
contract normative rather than aspirational.

It lives in the engine repository and runs against no interface at all, which is the property
that keeps the boundary honest — logic that leaked into the interface cannot be tested here,
and its absence shows up as a gap.

### Interface tests

**Unit and component tests**, `npm test`: the interface's own logic under Vitest — the body's
round trip between text on disk and the editor, citations, claims, splitting, moving — with
jsdom where an editor has to exist.

**Browser checks**, `npm run e2e`: the interface in a real Chromium, with a stub engine where
the shell would be. Each file in `e2e/checks/` replaces `window.__TAURI_INTERNALS__` before the
page loads, so every `invoke` reaches a stub that answers the way the real command does and
records what it was asked. They catch what jsdom cannot: a node view that draws nothing, tools
that scroll out of reach, a drag that lands on the wrong topic, a selection ProseMirror never
saw, words still in the editor when the window closes. Each check is named for the behaviour it
holds, so a failure reads as the bug it is.

What they cannot catch is anything on the far side of the stub. A change to the contract has
to reach the stubs too, or they go on answering the old way; and the real window draws with
WebKitGTK, not Chromium, which is what the walkthrough before a release is for.

End-to-end journeys through the real window and engine are not built: create a library → write
a document → save a source → cite it → see the reference list; and create a work → add editions
→ toggle panes. Kept deliberately few when they are — they are slow and brittle, and the risks
that matter are one layer down.

### Manual verification

The release checklist in [Packaging for Fedora](packaging-fedora.md#verifying-a-build),
including the offline run and the uninstall check.

## Fixtures

A set of small libraries checked into the engine repository, in
`crates/lc-engine/tests/fixtures/`, each opened from a copy as a person's library is:

| Fixture | Exercises | Exists |
| ------- | --------- | ------ |
| `minimal` | An empty library | Since M1 |
| `damaged` | Broken front matter, duplicate identifiers, an orphaned citation, a broken source and topic, a person's own notes left beside the documents | Since M1 |
| `v1`, `v2`, … | One library per historical format version, frozen forever | `v1` since M1 |
| `parallel` | The Russian/Finnish work, including misalignment and a repeated chorus | With M3 |

Two fixtures this page once planned are covered another way. Every source type and every
disambiguation case is a case in the engine's APA suite (`tests/apa/`) and its citation tests,
rule by rule, which shows exactly which rule broke; and `v1` holds every source type besides.
Cyrillic and Finnish text and filenames are in `v1` and in the engine's shared test library;
sorting by the rules of a language rather than by character is not modelled yet — see the
[citation model](citation-model.md#the-reference-list).

`damaged` is the one people skip. It is also the one that decides whether a user with a
half-broken library gets a diagnostic or gets nothing.

`v1` is frozen by a test that holds a hash of its bytes. A format change makes `v2` beside it,
written by the engine that writes the new format; `v1` stays, and proves the old format still
opens.

## In CI

On every pull request: engine unit tests, filesystem tests, contract tests, both property
tests, interface component tests, the browser checks in Chromium, clippy and rustfmt, the
interface's linter and type check, a check that the engine is pinned to a tagged release in
both `Cargo.toml` and `Cargo.lock`, and `bash docs/check-docs.sh`.

On a release tag: everything above, plus the RPM and Flatpak builds and the manual checklist.
